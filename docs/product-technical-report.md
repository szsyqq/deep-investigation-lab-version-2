# Deep Investigation Lab V2 产品技术报告

**副标题：从开放式问题到可核查调查报告的系统原理、生产流程与工程治理**

版本：2.0  
适用读者：产品经理、内容产品负责人、研究负责人、技术项目经理与协作开发者  
更新日期：2026-07-25

---

## 执行摘要

Deep Investigation Lab V2（下称 DIL V2）不是一个“输入题目、输出 HTML”的文章生成器，而是一套将调查研究拆成可检查中间产物的内容生产系统。它解决的核心问题并非语言生成质量，而是生成式系统在长期使用中常见的四类失控：

1. 研究方法存在于聊天上下文，无法稳定复用；
2. 图表根据“有没有数字”生成，而不是根据“要证明什么”生成；
3. 修改直接作用于成文页面，导致补丁式硬插入；
4. 每篇报告自带页面框架，修复一处可能影响多篇旧报告。

DIL V2 通过三个结构性变化解决这些问题：

- **把研究过程产品化**：研究请求必须依次经过范围、证据、主张、结构、视觉和发布六道关卡。
- **把编辑判断数据化**：证据、主张、视觉和人工修改分别保存，聊天反馈不再是一次性信息。
- **把内容与渲染分离**：每篇报告只保存结构化研究包，网站框架由共享应用统一渲染。

系统当前已经具备研究路由、研究包生成、证据引用完整性校验、视觉模式选择规则、修改分级、共享网站框架、GitHub Pages 自动发布和操作手册。下一阶段的重点是把示例性结构进一步发展为“真实报告自动渲染器”和“可操作的编辑决策后台”。

## 1. 产品定位与设计边界

### 1.1 产品要解决的任务

用户只需要表达调查意图，例如：

> 调查空客为什么订单增长，但交付和现金流同时承压。

系统需要完成的不只是写文章，而是：

1. 判断这是一项主体研究还是话题研究；
2. 把模糊意图转换为可检索、可证伪的问题树；
3. 搜集并记录可追溯证据；
4. 从证据中形成受约束的主张；
5. 为主张选择恰当的叙事结构和视觉表达；
6. 在共享网站框架中发布；
7. 在后续修改中保护已经确认的内容；
8. 把人工修改沉淀为下一次可调用的经验。

### 1.2 不在当前范围内的事项

DIL V2 当前不以以下能力为目标：

- 自动训练或微调基础模型；
- 在没有证据的情况下自动完成事实判断；
- 为每一章强制生成图表；
- 直接把所有 V1 报告批量迁移；
- 建设复杂 CMS、用户权限或数据库后台；
- 提供投资建议、股价预测或自动交易结论。

明确边界的原因是：系统首先需要保证研究产物的可解释性和可维护性，再扩展自动化程度。

## 2. 从 V1 到 V2：问题如何被重新定义

### 2.1 V1 的实际维护症状

对 V1 公开仓库的只读审计发现，正式门户下存在 21 个报告入口，仓库内包含约 232 个 HTML 文件，以及大量版本归档、注入、修复、统一和清理脚本。其主要问题不是“页面不好看”，而是内容、图表和页面结构过度耦合。

典型症状包括：

- 新报告复制旧报告框架，形成页面结构漂移；
- 图表逻辑与正文写在同一个 HTML 中，难以独立验证；
- 修改时模型只看到最终文章，不知道章节职责和已确认内容；
- 同一个全局脚本需要兼容多种历史页面结构；
- 修复动作以 DOM 或选择器为单位，缺乏报告级隔离；
- 版本归档保存了结果，但没有保存“为什么这样改”的决策。

### 2.2 根因模型

V1 的工作流可以抽象为：

> 研究请求 → 长篇正文 → 单页 HTML → 发布

中间缺少可验证状态，因此任何修改都只能直接作用于最终成品。系统无法回答：

- 当前核心问题是什么？
- 哪些事实已确认？
- 哪些段落承担什么论证职责？
- 某张图究竟在支持哪条主张？
- 哪些区域已经人工批准，不应随意重写？

### 2.3 V2 的解决原则

V2 将工作流改造为：

> 研究请求 → 研究简报 → 证据账本 → 主张地图 → 视觉计划 → 编辑状态 → 发布包 → 共享渲染器

每一步都形成独立文件，每个文件只承担一种职责。这样可以把错误定位在具体层级，而不是每次重写整篇文章。

## 3. 系统总体架构

### 3.1 四层架构

#### 第一层：研究控制层

负责理解用户请求、识别研究类型、限定范围、建立问题树和反证条件。核心产物是 `brief.json`。

#### 第二层：编辑知识层

负责记录证据、主张、视觉选择与人工修改。核心产物包括：

- `evidence-ledger.json`
- `claim-map.json`
- `visual-plan.json`
- `editorial-state.json`

#### 第三层：内容发布层

负责把已经确认的标题、摘要、章节、来源和视觉引用组织为 `publication.json`。它是编辑系统与网站之间的合同。

#### 第四层：共享渲染层

由 Next.js 应用统一提供导航、排版、视觉组件和响应式规则。所有报告共享这套框架，不再复制独立页面基础设施。

### 3.2 数据流与控制流

数据流回答“内容往哪里走”，控制流回答“什么时候允许进入下一步”。

数据流：

> 用户请求 → brief → evidence → claims → visuals → publication → web

控制流：

> 范围确认 → 证据充分 → 主张可追溯 → 结构明确 → 视觉合理 → 校验通过 → 发布

两者必须同时存在。只有数据流而没有关卡，系统仍会快速生成未经核查的页面；只有关卡而没有结构化文件，规则仍会退化为提示词。

### 3.3 报告隔离原则

每篇报告位于：

`content/reports/<slug>/`

报告 A 的事实、主张、视觉和编辑状态不得被报告 B 读取或修改。共享代码只提供展示能力，不保存任何单篇报告状态。这一原则避免“修复新文章导致旧文章图表失灵”。

## 4. 研究任务的识别与创建

### 4.1 为什么必须先分类

主体研究和话题研究虽然都需要检索资料，但问题结构不同。

- 主体研究的最终问题指向一个有边界的对象，如公司、人物、机构或产品。
- 话题研究的最终问题指向跨主体的现象，如政策、行业、事件、市场或社会议题。

如果不分类，系统容易把话题研究写成若干公司简介，或把公司研究写成泛泛的行业综述。

### 4.2 分类原理

系统判断“最终解释对象”，而不是简单统计关键词。

示例：

- “调查空客为什么交付下降”属于主体研究；
- “调查航空供应链短缺为何持续”属于话题研究；
- “调查电动车价格战，包括特斯拉的作用”仍属于话题研究。

代码中的初始分类器使用关键词和已知主体信号做确定性路由；Codex 在真实执行时还要结合语义对路由结果进行复核。

### 4.3 操作过程

1. 用户在 Codex 中提出自然语言请求；
2. 项目级 `AGENTS.md` 触发 `deep-investigation` Skill；
3. Skill 要求先执行研究创建指令；
4. `new-research.mjs` 分类请求并生成 slug；
5. 系统在独立目录生成六个研究文件；
6. Codex 补齐 `brief.json`，但此时不得直接写结论。

命令示例：

`npm run research:new -- "调查低空经济行业的真实需求与政策影响"`

### 4.4 形成的产物

初始研究包包括：

- `brief.json`：研究边界和问题；
- `evidence-ledger.json`：证据；
- `claim-map.json`：主张；
- `visual-plan.json`：视觉表达；
- `editorial-state.json`：批准状态和修改决策；
- `publication.json`：最终发布内容。

### 4.5 注意事项

- 分类只有两个主路由，不增加含义模糊的“混合研究”类型；
- 分类结果允许人工修正，但修正必须发生在研究开始前；
- slug 是技术标识，不等同于最终标题；
- 创建研究包不代表已经完成研究，只代表建立了工作空间；
- 不得在此阶段预设结论，否则后续检索会产生确认偏误。

## 5. 六道研究关卡的详细流程

## 5.1 Gate 1：研究范围

### 形成原理

开放式问题通常同时包含对象、时间、地区、业务维度和价值判断。范围关卡把这些混合信息拆解为可执行研究合同，防止研究过程中不断扩大问题。

### 操作步骤

1. 保留用户原始请求；
2. 确定 `researchType`；
3. 写出一个核心问题；
4. 拆成若干可验证子问题；
5. 写明纳入范围和排除范围；
6. 指定研究截止日期、时间区间和地域；
7. 列出可能推翻初步方向的证据。

### 通过条件

- 核心问题可以被证据回答；
- 子问题之间没有明显重复；
- 范围足以支持一篇完整报告，但不无限扩张；
- 至少有一项反证条件；
- 研究截止日期明确。

### 注意事项

- “全面研究”不等于无限搜集；
- 排除投资建议、未经授权的个人隐私和无法核实的传闻；
- 研究截止日期之后发生的事实不得混入当前版本；
- 若用户的问题本身带有强结论，应将结论改写为待检验假设。

## 5.2 Gate 2：证据账本

### 形成原理

文章中的事实如果只保留脚注序号，后续修改时很难判断来源是否仍然适用。证据账本把来源视为可管理对象：每条来源都有身份、时间、口径、覆盖问题和可信度。

### 来源优先级

1. 法律、监管、交易所和政府原始文件；
2. 公司公告、财报、官网与正式演讲；
3. 学术论文、行业标准和权威数据库；
4. 高质量新闻机构；
5. 专业人士或相关方的公开陈述；
6. 社交平台和论坛，只作为调查线索。

### 操作步骤

1. 按子问题建立证据需求清单；
2. 优先寻找原始材料；
3. 记录标题、发布者、URL、发布日期和访问日期；
4. 用自己的语言写来源摘要；
5. 记录统计口径、币种、单位和时间区间；
6. 标记来源覆盖的子问题；
7. 标记可信度与潜在利益关系；
8. 遇到冲突时同时保留两边证据，不直接删除其中一方。

### 通过条件

- 每个关键子问题至少有可用证据；
- 核心数字能够回到原始来源；
- 重大事实尽可能交叉验证；
- 冲突证据已被标记；
- 来源的时间和口径可解释。

### 注意事项

- “未单独披露”不等于“不存在”；
- 注册获批、正式上市和开始交易是不同事件；
- 净利润、归母净利润和扣非净利润不得混用；
- 媒体转述应尽量回查被引用的原始材料；
- 不为了形成漂亮图表而推算没有依据的数据拆分。

## 5.3 Gate 3：主张地图

### 形成原理

证据不是文章。主张地图负责把证据转换成可讨论的判断，同时保留事实与分析之间的边界。

主张分为：

- `fact`：来源直接支持；
- `analysis`：基于多项事实的解释；
- `unverified`：尚未解决；
- `forecast`：附条件的未来判断。

### 操作步骤

1. 从证据中提取事实句；
2. 合并重复或同义事实；
3. 为每条主张分配唯一 ID；
4. 绑定支持证据；
5. 记录反证或替代解释；
6. 标记置信度和状态；
7. 从主张之间的关系形成全文核心论点。

### 通过条件

- 每条发布主张至少绑定一项证据；
- 关键分析通常需要多项证据共同支持；
- 反证没有被隐藏；
- 推断被明确标记为分析；
- 核心论点能够回答研究简报中的核心问题。

### 注意事项

- 相关性不自动构成因果关系；
- 不能用来源的语气强度替代证据强度；
- 一条证据可以支持多条主张，但必须说明支持的是哪一部分；
- 当证据无法支持确定结论时，应保留不确定性，而不是补足语言。

## 5.4 Gate 4：编辑结构

### 形成原理

传统 AI 报告常按“公司概况—行业—业务—财务—风险”机械分章。DIL V2 要求每章承担一个论证职责，并推动读者更接近核心问题的答案。

### 操作步骤

1. 为每章定义 `sectionPurpose`；
2. 指定本章使用的主张 ID；
3. 确定章节之间的推进关系；
4. 检查同类事实是否被分散到不同章节；
5. 为导语设置核心张力；
6. 为结尾设置对核心问题的回扣；
7. 删除只提供背景、不推动论证的冗余部分。

### 通过条件

- 一章只承担一个主要职责；
- 章节顺序体现因果、时间、对比或问题递进；
- 正文不是证据清单；
- 导语、章节和结尾围绕同一个核心问题；
- 新增材料有明确归属位置。

### 注意事项

- 新材料若改变主张，不应直接追加到章节尾部；
- 当反馈涉及五个以上相互关联问题时，应考虑结构性重写；
- 不把每个分析维度都变成独立章节；
- 已批准章节必须记录，后续修改默认保护。

## 5.5 Gate 5：视觉规划

### 形成原理

图表类型不是表达模式。折线图、柱状图和表格只是组件；真正的编辑决策是“读者需要理解哪一种关系”。

视觉规划顺序为：

> 主张 → 读者结论 → 证据 → 关系类型 → 表达模式 → 组件

### 操作步骤

1. 写出候选视觉支持的 `editorialClaim`；
2. 写出读者三秒后应理解的 `readerTakeaway`；
3. 列出使用的证据 ID；
4. 判断视觉是否比一句简洁正文更有效；
5. 识别矛盾、因果、比较、趋势、时间、分布、网络或风险关系；
6. 选择表达模式；
7. 最后选择组件；
8. 设计结论型标题、注释和来源；
9. 检查移动端可读性。

### 核心模式

- `contradiction`：指标方向冲突；
- `causality`：机制经过多个环节传导；
- `comparison`：同口径对象比较；
- `trend`：连续变化本身是证据；
- `timeline`：阶段和转折比数值更重要；
- `distribution`：集中度或构成是核心；
- `network`：主体关系是核心；
- `risk`：概率、影响或情景有证据支持；
- `prose-only`：可视化不能降低理解成本。

### 通过条件

- 图表标题表达结论；
- 图表能指出所支持的主张；
- 每项数据可回到证据账本；
- 组件与关系类型匹配；
- 正文与图表不是简单重复；
- 移动端仍能理解核心关系。

### 注意事项

- 不设置“每章至少一图”的配额；
- 没有共同口径时不得强行比较；
- 只有两个简单数字时，对比卡可能优于图表；
- 多个环节传导时，故事流程图可能优于三张折线图；
- 动画只有在帮助理解时才保留；
- `prose-only` 是正式决策，不是失败状态。

## 5.6 Gate 6：发布校验

### 形成原理

发布不是把页面上传，而是确认研究内容、引用关系、视觉计划和工程构建同时处于可交付状态。

### 操作步骤

1. 完成 `publication.json`；
2. 检查标题、摘要、章节、主张和视觉引用；
3. 执行研究包校验；
4. 运行自动测试；
5. 构建网站；
6. 发布到 GitHub Pages；
7. 检查公开链接；
8. 保存版本和变更记录。

### 当前校验命令

- `npm run research:validate`
- `npm test`
- `npm run build:pages`

### 通过条件

- 所有必需文件存在且 JSON 有效；
- claim 引用的 evidence ID 存在；
- visual 引用的 evidence ID 存在；
- 自动测试通过；
- 静态页面构建成功；
- 首页、手册和报告页面返回正常；
- GitHub Pages 部署成功。

### 注意事项

- 构建成功不代表事实正确，事实责任仍由前五道关卡承担；
- 发布失败优先看 GitHub Actions 日志，不在正文层盲目修改；
- 部署配置只维护一份；
- GitHub Pages 使用仓库子路径，链接和静态资源必须带正确 base path。

## 6. 修改机制：为什么不再“生搬硬套”

### 6.1 修改的四种深度

#### 证据更新

适用：数字、日期或来源更新，但主张和结构不变。  
过程：更新证据账本 → 检查受影响主张 → 修改对应句子和图表数据。

#### 局部重写

适用：表达不清、段落重复或注释需要改善，但章节职责不变。  
过程：读取章节职责和已批准状态 → 只改限定范围 → 重新校验引用。

#### 结构调整

适用：新材料改变论证顺序或章节职责。  
过程：先改主张地图 → 重排章节 → 更新视觉计划 → 最后重写正文。

#### 全文重写

适用：核心问题、主要结论发生变化，或多个结构问题互相影响。  
过程：保留证据账本 → 重新执行主张、结构和视觉关卡 → 生成新发布版本。

### 6.2 编辑状态如何形成

`editorial-state.json` 记录：

- 已批准章节；
- 锁定事实；
- AI 原建议；
- 人工接受、修改或拒绝；
- 最终选择；
- 修改原因；
- 涉及的表达模式和组件。

这是一种“可积累学习”，不是模型训练。系统学习的对象不是成文风格，而是编辑为何改变某个方案。

### 6.3 注意事项

- 一次人工选择不能立即升级为全局规则；
- 同类决策重复出现后，才应提出规则更新；
- 修改前必须读取当前编辑状态；
- 不得用修复当前报告为理由修改其他报告；
- 被锁定的事实只有在来源变化或人工明确要求时才更新。

## 7. 网站与发布工程

### 7.1 为什么使用共享应用

共享应用把网站框架视为产品基础设施：

- 导航、字体、颜色和响应式规则统一；
- 新报告只新增研究数据和路由；
- 组件修复可以经过测试后统一生效；
- 报告之间不共享运行状态；
- 不再为每篇报告复制全套 HTML、CSS 和 JavaScript。

### 7.2 双构建策略

当前项目保留两种构建路径：

- Sites/Vinext 构建：用于原先的 ChatGPT Sites 环境；
- Next.js 静态导出：用于公开 GitHub Pages。

由于 ChatGPT Sites 私有登录在当前环境无法正常使用，对外入口已切换为 GitHub Pages。静态导出设置包括：

- `output: export`
- 仓库子路径 `basePath`
- 静态资源 `assetPrefix`
- `trailingSlash`
- 无服务器依赖的预渲染页面

### 7.3 GitHub Pages 发布过程

1. 开发者将代码推送到 `main`；
2. GitHub Actions 检出代码；
3. 安装锁定依赖；
4. 校验研究包；
5. 运行自动测试；
6. 执行静态构建；
7. 上传 `out` 目录；
8. GitHub Pages 发布；
9. 公开地址无需登录即可访问。

### 7.4 注意事项

- 只有静态可预渲染功能可以直接部署到 GitHub Pages；
- 如果未来加入数据库、登录或服务端检索，需要独立后端；
- 项目路径包含 `#` 时，本地 Next.js 工具可能出现路径解析问题；应在无特殊字符路径中构建，GitHub Actions 不受影响；
- `main` 是自动发布分支，推送前必须通过校验；
- Actions 失败时应保留失败日志和对应提交 SHA。

## 8. 面向产品经理的日常操作流程

### 8.1 创建一项新研究

1. 在 Codex 中打开 V2 仓库；
2. 用自然语言提出研究请求；
3. 审核主体/话题分类；
4. 审核范围和反证条件；
5. 要求完成证据搜集，不直接催促成文；
6. 审核主张地图；
7. 审核章节职责；
8. 审核视觉计划，重点看“为什么使用”；
9. 生成发布包；
10. 执行校验和发布。

产品经理在每个阶段的关键问题分别是：

- 研究范围：我们到底在回答什么？
- 证据：哪些事实足以支撑判断？
- 主张：事实与解释是否分开？
- 结构：读者如何一步步得到答案？
- 视觉：这张图帮助理解了什么？
- 发布：来源、内容和页面是否同时可交付？

### 8.2 修改已发布研究

建议的反馈格式：

> 新增材料显示发动机短缺的影响可能持续更久。请先判断它属于证据更新还是结构调整；保护已批准的订单章节，并说明哪些主张和视觉需要变化。

避免只说：

> 把这段加进去。

前者提供了修改目标和保护边界，后者容易触发补丁式编辑。

### 8.3 发布与验收

发布前由产品经理确认：

- 核心问题与标题一致；
- 关键主张有来源；
- 待核实信息没有伪装成事实；
- 图表标题能独立表达结论；
- 正文与视觉互相补充；
- 移动端阅读顺序自然；
- 操作手册和报告链接正常；
- GitHub Actions 显示成功。

## 9. 维护与治理

### 9.1 三层维护频率

#### 高频：报告内容层

位置：`content/reports/`  
维护内容：研究范围、证据、主张、视觉、编辑状态和发布内容。

#### 按需：研究规则层

位置：`.codex/skills/deep-investigation/` 与 `docs/`  
维护条件：多个报告重复出现同一类问题，且已有足够决策记录。

#### 低频：网站框架层

位置：`app/`、构建配置与发布工作流  
维护条件：跨报告的展示、交互或发布能力需要升级。

### 9.2 版本治理

建议使用以下变化级别：

- Patch：事实更正、文案修复、样式修复；
- Minor：新增报告、模式或组件；
- Major：研究数据合同、工作流或渲染架构改变。

数据结构升级时，需要：

1. 更新 schemaVersion；
2. 提供旧数据迁移策略；
3. 更新校验器；
4. 增加回归测试；
5. 验证现有报告不受影响。

### 9.3 质量指标

建议逐步建立以下指标：

- 关键主张证据覆盖率；
- 主张被人工接受、修改、拒绝的比例；
- 视觉方案接受率；
- `prose-only` 使用率；
- 发布前校验失败类型；
- 报告修改影响范围；
- 从请求到可发布版本的周期；
- 发布后事实更正次数。

这些指标用于发现系统问题，不应被用来鼓励更多图表或更长文章。

## 10. GitHub 仓库架构与文件维护

### 10.1 当前仓库的总体结构

GitHub 仓库 `szsyqq/deep-investigation-lab-version-2` 同时承担四种职责：

1. **研究工作台**：保存 Codex 能识别和执行的调查流程；
2. **内容数据库**：用结构化文件保存每篇研究的证据、主张与编辑状态；
3. **网站源代码**：保存共享页面、样式和交互组件；
4. **发布流水线**：通过 GitHub Actions 自动校验并发布 GitHub Pages。

当前核心目录如下：

`AGENTS.md`  
项目最高层的代理规则。告诉 Codex 何时触发调查 Skill，并规定不得修改 V1、不得复制单页 HTML、不得跳过证据和校验。

`.codex/skills/deep-investigation/`  
调查研究 Skill。`SKILL.md` 保存主流程，`references/` 保存研究路由、视觉规划和修改协议，`agents/openai.yaml` 保存 Codex 界面元数据。

`content/reports/<slug>/`  
每篇报告的独立研究包。报告之间不得共享事实状态或编辑状态。

`app/`  
共享网站应用。首页、操作手册、工作台和报告路由都从这里渲染；`globals.css` 保存统一视觉系统。

`docs/`  
面向人和 Codex 的系统文档，包括研究协议、视觉协议、V1 审计、本技术报告源稿。

`scripts/`  
确定性工具，包括研究包创建、研究包校验和技术报告生成。适合把容易重复出错的操作固化为程序。

`tests/`  
自动测试。当前覆盖研究类型判断、研究包隔离和证据引用完整性。

`.github/workflows/`  
自动发布流水线。每次 `main` 更新后依次安装依赖、校验研究、运行测试、构建静态站点并发布。

`.openai/hosting.json`  
原 ChatGPT Sites 项目标识。由于当前对外发布已改为 GitHub Pages，该文件仍作为原部署记录保留，但不应存储密钥或业务数据。

`package.json` 与 `package-lock.json`  
定义运行命令和锁定依赖版本。

`next.config.ts`  
根据环境选择构建策略。GitHub Pages 模式启用静态导出、仓库子路径和资源前缀。

### 10.2 文件之间的依赖关系

仓库的关键依赖方向是：

> AGENTS / Skill → scripts → content → app → build → GitHub Pages

规则层可以读取内容层，但内容层不应复制规则；网站层读取发布内容，但不应成为事实来源；发布层只负责验证和交付，不应改变研究结论。

如果反向依赖失控，例如把证据直接写进组件，或把页面 DOM 当成研究数据，系统会重新出现 V1 的维护问题。

### 10.3 新文件进入后的维护顺序

#### 场景一：新增原始资料

1. 判断资料属于哪篇报告；
2. 不直接把 PDF、网页文字或截图写入正文；
3. 在 `evidence-ledger.json` 新增证据项；
4. 记录来源、时间、口径、摘要和可信度；
5. 检查它支持、修正还是反驳现有主张；
6. 更新受影响的 `claim-map.json`；
7. 必要时更新视觉与发布内容；
8. 执行校验和测试。

#### 场景二：新增一篇研究

1. 使用 `research:new` 创建独立目录；
2. 完成 brief；
3. 完成 evidence；
4. 完成 claims；
5. 完成结构和 visual plan；
6. 完成 publication；
7. 新增共享渲染路由，而不是复制旧页面；
8. 增加必要测试；
9. 推送 `main` 自动发布。

#### 场景三：新增视觉组件

1. 先确认它对应的表达模式，而不是因为“需要新图”；
2. 在视觉协议中定义适用和禁用条件；
3. 确定输入合同；
4. 在共享组件层实现；
5. 准备正常、数据不足和 `prose-only` 对照测试；
6. 在一篇实验报告验证；
7. 通过后再允许其他报告调用。

#### 场景四：新增规则或经验

1. 先写入某篇报告的 `editorial-state.json`；
2. 累积相似人工决策；
3. 形成规则更新建议；
4. 人工审核；
5. 更新 Skill 或参考文档；
6. 提升规则版本；
7. 对现有案例运行回归测试。

### 10.4 仓库维护注意事项

- `main` 是公开网站自动发布分支，不能把未通过校验的实验直接推入；
- 大型原始文件需要评估版权、体积和公开范围，不默认提交到公开仓库；
- 不在 JSON、代码或工作流中保存令牌、密码和私人信息；
- 修改 schema 时必须同步更新脚本、测试和迁移说明；
- 删除文件前先检查是否被报告、文档或工作流引用；
- 共享组件的改动风险高于单篇内容改动，应增加回归检查；
- V1 继续保持只读，迁移应通过显式导入流程完成。

## 11. 编写、修改与知识更新机制

### 11.1 当前已经形成的内容

当前版本已经完成：

- 项目级 `AGENTS.md` 规则；
- `deep-investigation` 调查 Skill；
- 主体研究与话题研究路由；
- 六文件研究包数据模型；
- 研究包创建与校验脚本；
- 证据引用完整性测试；
- 视觉表达协议与 `prose-only` 规则；
- 修改深度分类与编辑状态设计；
- 固定网站首页、工作台、操作手册和空客示例；
- GitHub Pages 静态构建与自动发布；
- 产品操作手册和本技术报告。

尚未完成但已明确接口的部分包括：

- `publication.json` 驱动的动态报告渲染；
- 自动化网页和 PDF 证据采集；
- 人工编辑决策界面；
- 完整 Pattern/Case/Decision 检索；
- 报告审批、撤回、归档和多用户协作。

### 11.2 新内容的编写机制

新报告应遵循“先结构、后正文”的编写顺序：

1. 用户请求保存在 brief；
2. 子问题决定检索计划；
3. 证据账本先于主张；
4. 主张地图先于章节；
5. 章节职责先于长篇正文；
6. 视觉计划先于组件实现；
7. publication 先于网站发布。

这套顺序的意义是：任何阶段出现问题，都可以返回上一层修改，而不必重写全部结果。

### 11.3 修改和更新的具体操作

#### 数据或来源变化

修改顺序：

> evidence → claim → visual → publication

不要只改页面显示数字，否则证据账本与发布内容会失去一致性。

#### 文章表达变化

先确认是否保持原 `sectionPurpose`。如果保持，只做局部重写；如果改变，先调整主张和章节结构。

#### 图表变化

先改 `visual-plan.json` 中的主张、模式、组件和理由，再修改共享组件或数据。不能直接在页面中替换一段图表代码而不记录编辑判断。

#### 工作流变化

先使用真实案例说明旧规则为何失败，再更新 Skill、参考文档和测试。工作流变更属于系统级更新，不应由单篇文章临时触发。

### 11.4 已有的自动更新机制

当前自动机制主要是工程自动化，而不是知识自动学习：

- 新研究包由脚本自动建立；
- 校验器自动检查文件和引用关系；
- 测试自动检查关键逻辑；
- 推送 `main` 后自动构建和发布；
- GitHub 保留每次变更历史，可以比较和回滚。

当前系统**不会**自动把每次聊天反馈写入全局规则，也不会自动修改 Skill。这是有意设计：单次反馈可能只适用于特定报告，自动升级全局规则会放大错误。

### 11.5 为什么仍需要人工知识更新工作流

需要设计一条半自动、人工批准的知识更新流程：

> 收集编辑决策 → 聚类重复修改 → 生成候选规则 → 案例回测 → 人工批准 → 更新 Skill/Pattern → 版本发布

人工环节必须保留在：

- 判断修改理由是否可泛化；
- 判断案例是否具有相同关系而非表面相似；
- 决定规则是否替换、补充或保持实验状态；
- 审核规则对旧报告是否产生副作用。

### 11.6 推荐的手动更新节奏

每篇报告结束：

- 补齐 editorial-state；
- 记录最重要的接受、修改和拒绝原因；
- 标记可能形成新规则的候选项。

每完成 5—10 篇报告：

- 汇总重复决策；
- 检查视觉模式接受率；
- 识别高频失败原因；
- 评审是否升级 Skill 或组件。

每个正式版本：

- 冻结规则版本；
- 运行回归测试；
- 更新技术文档；
- 发布变更摘要；
- 保留回滚点。

### 11.7 注意事项

- 自动发布不等于自动审核；
- 聊天历史不是可靠知识库；
- 人工决策若不记录，就不能形成稳定学习；
- 不要把审美偏好误写成事实规则；
- 不要因一次成功案例就增加全局模式；
- 规则更新必须能说明影响范围和回退方法。

## 12. 模型优化：怎样建立更好的研究模型

### 12.1 “更好的模型”不是只换一个更大的大模型

在本项目中，模型质量由五部分共同决定：

> 基础模型能力 × 上下文质量 × 工具可靠性 × 结构化反馈 × 评估机制

更大的模型可能提升推理和写作，但不能自动解决来源丢失、修改污染、图表错配和长期经验无法沉淀的问题。DIL V2 的优化重点应首先放在模型外部系统。

### 12.2 第一层：改善任务分解

把复杂任务拆成研究路由、证据、主张、编辑结构、视觉和发布多个阶段。每个阶段使用更窄的输入和输出，可以降低模型一次性处理整篇报告时的漂移。

优化方法：

- 为每个阶段建立明确 schema；
- 限制阶段可修改的文件；
- 为低置信度设计返回路径；
- 把不可逆发布动作放在最后；
- 对关键判断要求解释理由和反证。

### 12.3 第二层：改善上下文与检索

模型需要看到“当前任务最相关的内容”，而不是整个仓库。

优化方法：

- 研究开始只读取 brief 和路由规则；
- 形成主张时读取 evidence，不加载页面代码；
- 视觉规划时读取 claim、visual protocol 和相似案例；
- 修改时额外读取 editorial-state；
- 发布时读取 publication 和校验结果。

这种渐进披露可以减少上下文噪声，并降低把旧报告内容误带入新报告的概率。

### 12.4 第三层：建立 Pattern、Case 与 Decision 三层知识

#### Pattern

保存可复用编辑规则，例如“领先指标增长但结果恶化”。数量应少而稳定。

#### Case

保存 Pattern 在真实报告中的正面、反面和修订案例。模型通过相似案例理解规则如何落地。

#### Decision

保存 AI 建议、人类选择和修改原因。它最能体现真实编辑偏好。

三层分开的原因是：规则、案例和偏好具有不同稳定性，不能混成一篇自由笔记。

### 12.5 第四层：建立评估集

没有评估集，就无法判断模型是否真正改善。

建议建立四类测试：

1. **研究路由测试**：主体和话题边界是否稳定；
2. **证据测试**：是否正确引用、识别冲突和口径；
3. **编辑测试**：是否能选出正确章节职责和修改深度；
4. **视觉测试**：是否选择合适模式，是否知道何时不用图。

每类测试都应包含：

- 正常案例；
- 边界案例；
- 数据不足案例；
- 容易诱导错误的案例；
- 期望返回 `prose-only` 或“待核实”的案例。

评估指标不只看最终文字，还应看：

- 事实准确率；
- 证据覆盖率；
- 引用完整性；
- 人工修改量；
- 视觉建议接受率；
- 结构性返工次数；
- 对已批准内容的保护率。

### 12.6 第五层：选择模型与任务路由

不是所有阶段都需要同一模型：

- 分类、schema 校验和文件生成可使用确定性脚本或轻量模型；
- 跨来源综合、反证分析和结构重写需要更强推理模型；
- 文案润色可以在主张和结构锁定后使用语言能力强的模型；
- 发布校验尽量使用程序，不依赖模型“自我检查”。

这样可以在质量、速度和成本之间取得平衡。

### 12.7 第六层：何时考虑微调

在积累足够高质量 Decision 和 Case 之前，不建议直接微调。

满足以下条件后才值得评估：

- 至少有数百个结构一致的输入输出案例；
- 人工修改原因已标准化；
- 可以划分训练集、验证集和保留测试集；
- 目标行为稳定，例如分类、模式选择或标题风格；
- 使用检索和规则仍无法稳定解决问题。

微调更适合稳定、重复、可评分的子任务，不适合替代实时事实研究。

### 12.8 推荐的模型优化路线

阶段一：

- 完善 schema 和校验；
- 用真实报告建立 20—30 个高质量 Case；
- 记录至少 50 条人工 Decision；
- 建立第一版评估集。

阶段二：

- 加入相似案例检索；
- 对 Pattern 选择做离线回测；
- 比较不同模型在各阶段的质量和成本；
- 建立错误分类体系。

阶段三：

- 自动生成规则更新建议；
- 人工审核后升级知识库；
- 对稳定子任务尝试小规模微调；
- 始终保留原始证据和程序校验作为外部约束。

### 12.9 模型优化注意事项

- 不用最终网页美观程度代替研究质量；
- 不用模型自评分作为唯一评估；
- 不把训练材料中的事实当作实时事实；
- 不让模型自动修改自己的最高层规则；
- 不在没有保留测试集时宣称模型已经改善；
- 优先优化错误成本最高的环节，如事实、引用和结构，而不是语气。

## 13. 风险、限制与故障处理

### 13.1 研究风险

- 来源过时：记录访问日期和研究截止时间；
- 来源冲突：并列保存并解释口径；
- 推断过度：区分 fact 与 analysis；
- 确认偏误：在 brief 中预先写反证条件；
- 假精确：无可靠依据时使用范围和不确定性。

### 13.2 产品风险

- 工作流过重：简单任务也被强制执行过多步骤；
- JSON 对非技术编辑不友好；
- 规则不断增长导致 Skill 上下文过长；
- 人工决策记录不完整，系统无法真正积累经验；
- 模式库过早扩张，出现大量同义模式。

应对方式是保留最小必要关卡、渐进披露参考资料，并用真实报告验证新增规则。

### 13.3 工程风险

- GitHub Actions 权限或 Pages 未启用；
- 仓库子路径造成资源 404；
- 本地特殊字符路径影响构建；
- 静态托管无法支持未来服务端功能；
- 依赖升级破坏构建。

故障处理顺序：

1. 确认失败发生在研究校验、测试、构建还是部署；
2. 查看对应命令或 Actions 步骤；
3. 在最小范围修复；
4. 重跑失败关卡；
5. 检查公开 URL；
6. 记录对维护规则有长期价值的原因。

## 14. 后续开发路线

### 阶段一：真实报告渲染器

目标：让 `publication.json` 直接渲染为正式报告，而不是在页面中硬编码示例内容。

主要工作：

- 定义稳定的发布 schema；
- 创建章节、数据卡、来源和视觉组件；
- 增加动态报告路由；
- 建立空数据和异常数据状态；
- 对示例报告完成回归测试。

### 阶段二：证据采集助手

目标：降低记录来源和口径的成本。

主要工作：

- 从网页、PDF和公告提取元数据；
- 保存访问时间和关键摘要；
- 检测相同数字的口径冲突；
- 对过时来源发出提示；
- 生成来源完整性报告。

### 阶段三：编辑决策工作台

目标：让非程序员可以审核主张、视觉和修改建议。

主要工作：

- 展示 AI 建议与人工最终选择；
- 支持接受、修改和拒绝；
- 记录原因；
- 统计重复决策；
- 生成人工审核的规则升级建议。

### 阶段四：表达模式库扩展

目标：从当前核心关系扩展到关系网、地理分布、情景和复杂风险。

扩展原则：

- 每个新模式至少有两个真实案例；
- 明确适用和不适用条件；
- 必须允许退回 `prose-only`；
- 新组件必须通过移动端测试；
- 不为凑数量创建同义模式。

### 阶段五：后台与协作

目标：管理研究状态、审核、版本和发布。

需要评估：

- 是否引入数据库；
- 用户和角色模型；
- 审核流；
- 草稿与正式版本；
- 发布、撤回与归档；
- 数据备份和权限审计。

## 15. 结论

DIL V2 的核心价值不在于“让 AI 写得更像记者”，而在于让研究生产具备可解释、可核查、可修改和可维护的系统结构。

它把一次性生成拆成一系列可观察状态：

- 为什么研究这个问题；
- 使用了哪些证据；
- 形成了哪些主张；
- 为什么采用这种叙事和视觉；
- 人工为什么修改；
- 什么条件满足后才能发布。

当这些判断不再只存在于聊天记录，系统才可能随着使用积累能力。后续开发应继续围绕这一原则：优先增加可追溯性、可审阅性和局部可修改性，而不是增加更多自动生成页面或更多图表类型。

## 附录 A：研究包文件职责

### brief.json

研究合同。保存请求、分类、范围、核心问题、子问题和反证条件。

证据仓库。保存来源、日期、摘要、口径、可信度和冲突状态。

论证结构。保存事实、分析、待核实、预测及其证据关系。

视觉决策。保存主张、读者结论、模式、组件、数据和禁用方案。

编辑记忆。保存批准区域、锁定事实和人工决策。

发布合同。保存标题、摘要、章节、主张引用、视觉引用和来源。
