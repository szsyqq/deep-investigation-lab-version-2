## 执行摘要

Deep Investigation Lab V2 是一个完整的调查报告生产系统，不是单独的图表工具。

用户只需要提出一个调查任务。系统负责判断是主体研究还是话题研究，组织不同编辑视角形成研究议程，进行可以反复返回的全网研究，保存来源和过程底稿，撰写完整文字初稿，增加真正解释论点的图表，完成相似性、事实和结构审核，再根据分析师意见反复修改。最终文件先进入内部试读，得到明确批准后才正式发布。

产品对用户只呈现七个阶段：

> 接收任务 → 讨论与研究 → 框架与底稿 → 文字初稿 → 视觉编辑 → 审核与修改 → 内部预览与正式发布

证据编号、JSON 状态、自动校验和网站构建属于后台保障，不应成为分析师日常使用时的负担。

## 1. 产品要解决什么问题

### 1.1 目标

系统需要稳定完成四件事：

1. 把一个开放式问题变成全面、可追溯的调查；
2. 把研究材料组织成完整、连贯、有论点的文章；
3. 允许分析师多轮修改而不产生“硬插入”和结构破坏；
4. 让所有报告共享一个网站框架，并区分内部试读和正式发布。

### 1.2 它不是什么

- 不是搜索结果摘要器；
- 不是一次性网页生成器；
- 不是见到数字就画图的图表工具；
- 不是依靠聊天记忆自动学习的黑箱；
- 不是每篇文章重新复制一次网站代码。

### 1.3 最重要的产品原则

> 报告是持续生长的产品状态，而不是一次生成的静态文件。

系统必须保存研究过程、当前完整文稿、人工意见和发布状态，才能在下一次修改时理解上下文。

## 2. 七阶段报告生产流程

### 2.1 阶段一：接收任务与研究分类

#### 形成原理

同一句“调查”可能指向不同的最终对象。公司、机构、人物和产品属于主体研究；行业、政策、事件、趋势和社会现象属于话题研究。两类研究需要不同的问题清单，但可以共享后续生产流程。

#### 操作过程

1. 接收用户原始任务；
2. 识别最终问题指向；
3. 判断为 `entity` 或 `topic`；
4. 确认核心问题、时间和地域范围；
5. 记录排除项和可能推翻初步假设的证据；
6. 创建该报告独立的底稿目录。

#### 主要产物

- `brief.json`：机器可读的任务说明；
- `workflow-state.json`：当前生产阶段；
- 整套空白底稿文件。

#### 注意事项

- 分类只决定研究起点，不决定文章目录；
- 这一阶段不能提前写结论；
- 请求不清楚时，只询问真正影响研究方向的问题。

### 2.2 阶段二：讨论团与反复研究

#### 形成原理

好的调查不是从关键词搜索开始，而是从“读者真正想知道什么”开始。讨论团代表不同编辑视角，不要求使用六个昂贵模型；它可以由同一个模型依次扮演固定角色，也可以由多个代理并行工作。

建议角色：

- 主编：判断核心新闻价值；
- 行业分析师：补充市场、商业和历史背景；
- 调查研究员：寻找事实、矛盾和关键来源；
- 反方审稿人：寻找替代解释和反证；
- 数据编辑：统一指标、口径和时间范围；
- 读者代表：判断哪些问题最值得解释。

#### 操作过程

第一轮先构建整体面貌：

1. 讨论读者和市场最关心的问题；
2. 搜索官方文件、公司材料、权威数据库和高质量报道；
3. 记录事实、口径、发布时间和访问时间；
4. 标记冲突、空白和待核实问题；
5. 汇总当前发现。

随后进入研究循环：

```text
搜索和阅读
→ 形成阶段性发现
→ 讨论矛盾和遗漏
→ 产生新的研究问题
→ 补同行、历史、机制或反证
→ 再次判断
```

#### 什么时候停止研究

- 主要问题已经获得可靠回答；
- 核心判断有多个角度的证据；
- 重要反方解释已经被考虑；
- 关键口径和时间边界清楚；
- 新搜索结果开始大量重复；
- 无法确认的内容已明确列为待核实。

#### 主要产物

- `discussion.md`；
- `research-notes.md`；
- `sources/`；
- `evidence-ledger.json`；
- `workflow-state.json.researchLoops`。

#### 注意事项

- 不以固定搜索次数代替研究充分度；
- 社交媒体通常只作为线索；
- 冲突证据必须保留；
- 来源底稿属于当前报告，不能混入其他报告。

### 2.3 阶段三：形成框架与底稿

#### 形成原理

研究材料不会自动成为文章。框架的任务是决定文章要证明什么、每一章负责什么，以及证据如何推动读者理解。

#### 操作过程

1. 从研究结果中提取中心矛盾或核心问题；
2. 区分事实、分析、待核实和条件性预测；
3. 为每项主张绑定证据编号；
4. 为每一章定义唯一的章节职责；
5. 写明本章结论、证据和与前后章节的关系；
6. 检查目录是否只是机械的业务维度罗列；
7. 形成可供分析师评审的框架。

#### 主要产物

- `claim-map.json`；
- `outline.md`。

#### 注意事项

- 目录必须服务论点，不以“业务、财务、市场、风险”机械平铺；
- 每章只承担一个主要职责；
- 证据不足的主张不能进入正式框架。

### 2.4 阶段四：撰写完整文字初稿

#### 形成原理

初稿首先是一篇文章，不是网页组件集合。只有完整文字能够检验论证是否连贯、章节是否自然，以及读者能否理解因果和争议。

#### 操作过程

1. 按 `outline.md` 撰写开篇、正文和结论；
2. 每章围绕一个核心问题展开；
3. 让事实、证据、原因、影响和判断自然衔接；
4. 区分来源事实与分析判断；
5. 在写作中发现证据空白时返回第二阶段；
6. 新材料改变章节职责时先更新框架；
7. 将当前完整文章保存到 `draft.md`。

#### 通过条件

- 不看图表也能理解文章主线；
- 章节之间不存在明显跳跃；
- 新内容不是附加在旧稿末尾；
- 关键判断都能找到证据；
- 文章篇幅和深度满足调查任务。

#### 注意事项

- 不以模糊表达填补证据不足；
- 不把来源摘要简单拼接成正文；
- 不在这一阶段为了页面好看拆碎文章。

### 2.5 阶段五：增加图表与视觉表达

#### 形成原理

视觉编辑服务正文论点。系统先问“读者需要理解什么”，最后才决定用折线图、时间线或故事图。

#### 操作过程

1. 从初稿中提取候选视觉主张；
2. 写出读者看完后应理解的结论；
3. 确认证据和数据口径；
4. 判断视觉是否降低理解成本；
5. 识别关系类型：矛盾、因果、比较、趋势、时间、分布、关系或风险；
6. 最后选择具体组件；
7. 将图表放入最合适的叙事位置；
8. 检查是否与正文重复；
9. 保存到 `visual-plan.json`。

#### 注意事项

- 允许输出 `prose-only`；
- 图表标题要表达结论，不能只写主题；
- 不能从相关性暗示因果；
- 图表必须绑定证据编号；
- 移动端如果更难理解，应改用更简单形式。

## 3. 审核与人工修改

### 3.1 相似性和重复检查

检查是否存在：

- 大段接近来源原文；
- 引语未标明；
- 不同章节重复表达相同结论；
- 同一数字在正文和图表中无意义重复；
- 为追求篇幅而重复背景。

系统应称其为“来源相似性检查”，不能仅靠自动工具作出法律意义上的抄袭判断。

### 3.2 事实和结构审核

事实审核关注：

- 数字、日期、身份和口径；
- 来源是否真的支持相应主张；
- 事实和分析是否明确区分；
- 反方观点是否遗漏。

结构审核关注：

- 开篇是否提出核心问题；
- 每章是否完成自己的职责；
- 结论是否由前文自然推出；
- 图表是否位于正确位置；
- 是否存在可以删除或合并的章节。

审核结果写入 `review.md`。

### 3.3 人工意见如何处理

系统收到分析师反馈后，先判断修改级别：

- `evidence-update`：更新事实、数字或来源；
- `local-rewrite`：局部表达调整；
- `structural-revision`：章节职责或顺序变化；
- `full-rewrite`：核心问题或中心论点变化。

#### 修改流程

```text
接收意见
→ 把意见翻译成具体问题
→ 判断修改级别
→ 确定受影响文件和章节
→ 先更新证据或框架
→ 重写完整受影响区域
→ 检查前后衔接
→ 更新图表
→ 重新审核
→ 记录分析师决定
```

分析师意见同时进入：

- `revisions.md`：人类可读的修改历史；
- `editorial-state.json`：机器可读的决策记忆。

#### 注意事项

- 结构问题不能靠追加一段话解决；
- 修改后必须重新阅读前后章节；
- 已批准章节默认保持稳定；
- 一次特殊意见不能自动改写全局规则。

## 4. 内部预览与正式发布

### 4.1 为什么分两层

调查报告经常需要让分析师、编辑或内部读者先浏览。如果预览和正式发布没有区分，测试内容、待核实问题或示例数据可能被误当成正式结论。

### 4.2 发布状态

- `researching`：研究中；
- `draft`：初稿；
- `review`：审核中；
- `analyst-confirmation`：等待分析师确认；
- `internal-preview`：内部试读；
- `approved`：批准发布；
- `published`：正式发布；
- `update-required`：需要更新。

### 4.3 内部试读页面

内部预览应显示：

- 当前版本和试读标签；
- 更新时间；
- 分析师确认状态；
- 尚未解决的问题；
- 数据截止日期；
- 是否允许进入正式发布。

### 4.4 正式发布条件

1. 分析师明确批准；
2. 关键事实和来源检查通过；
3. 结构和图表审核通过；
4. 不存在未处理的关键疑问；
5. 研究校验、测试和生产构建通过；
6. `publication.json.status` 被更新为 `published`。

## 5. 内部系统怎样组织

### 5.1 一篇报告一个底稿目录

```text
content/reports/<slug>/
├── brief.json
├── workflow-state.json
├── discussion.md
├── research-notes.md
├── sources/
├── evidence-ledger.json
├── claim-map.json
├── outline.md
├── draft.md
├── visual-plan.json
├── review.md
├── revisions.md
├── editorial-state.json
└── publication.json
```

### 5.2 为什么同时使用 Markdown 和 JSON

Markdown 适合分析师阅读、批注和修改；JSON 适合程序校验、网页渲染和状态管理。

系统不要求分析师直接编辑 JSON。正常情况下，分析师用自然语言提出任务和意见，Codex 负责同步更新人类底稿和机器状态。

### 5.3 三层架构

#### 内容层

位于 `content/reports/`，保存每篇报告独立的研究和写作状态。

#### 规则层

位于 `.codex/skills/deep-investigation/` 和 `docs/`，规定研究、修改、图表和发布原则。

#### 网站层

位于 `app/`，保存共享导航、排版、报告组件、内部预览和正式页面。新报告不能复制这一层。

## 6. 日常操作

### 6.1 创建报告

自然语言：

> 调查某家公司最近三年增长放缓的原因，并与主要同行比较。

命令：

```bash
npm run research:new -- "调查任务"
```

### 6.2 推进阶段

```bash
npm run research:advance -- <slug> --to=drafting
npm run research:advance -- <slug> --to=visual-editing
npm run research:advance -- <slug> --to=review-revision
```

### 6.3 进入预览和发布

```bash
npm run research:advance -- <slug> --to=internal-preview
npm run research:approve -- <slug> "分析师确认意见"
npm run research:advance -- <slug> --to=published
```

正式发布命令必须在分析师已经明确批准后使用。

### 6.4 校验

```bash
npm run research:validate
npm test
npm run build
```

## 7. 系统如何积累经验

### 7.1 不依赖聊天记忆

聊天中的一次纠正只能影响当次上下文。要让系统持续改进，必须把人工决定保存为正式记录。

### 7.2 保存三类知识

- Pattern：稳定的表达或编辑规则；
- Case：正面、反面和修订案例；
- Decision：分析师每次接受、修改或拒绝的原因。

### 7.3 推荐更新机制

```text
积累人工决定
→ 发现重复修改模式
→ 生成规则更新建议
→ 人工审核
→ 更新技能或 Pattern
→ 运行回归测试
```

这是一种人工审核式学习，而不是让系统根据一次修改自动改变所有报告。

## 8. 当前已经实现什么

- 主体研究与话题研究分类；
- 完整底稿目录自动创建；
- 七阶段工作流状态；
- 研究循环记录结构；
- 证据、主张和视觉引用校验；
- 修改级别分类；
- 内部试读与正式发布状态；
- 共享网站框架；
- 操作手册和示例报告；
- GitHub Actions 自动校验、测试、构建和部署。

## 9. 下一步开发重点

### 第一优先级：真实报告通用渲染器

让 `publication.json`、`draft.md` 和 `visual-plan.json` 自动生成共享报告页面，替代示例页面硬编码。

### 第二优先级：分析师审阅台

支持逐段评论、疑问、修改范围判断、版本比较、接受或拒绝，以及正式批准。

### 第三优先级：来源采集与底稿管理

自动保存网页信息、文件快照说明、发布时间、访问时间、摘录、冲突和覆盖问题。

### 第四优先级：内部报告管理

提供研究中、审核中、内部试读、批准、已发布和待更新列表。

### 第五优先级：经验治理

统计重复人工决定，提出规则更新建议，并通过人工审核和测试后升级系统。

## 10. 结论

Deep Investigation Lab V2 的核心不是增加更多步骤，而是把真实报告生产中的必要状态保存下来。

用户看到的流程应该简单：

> 提出任务，确认研究方向，阅读初稿，提出意见，内部试读，批准发布。

系统在后台负责研究循环、来源追溯、结构完整性、视觉规划、修改范围和发布校验。这样既能保持使用简单，也能避免一次性生成、修改生硬、图表失灵和网站反复重建。
